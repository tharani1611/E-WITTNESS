# 4. PHASE 31 — USER PROFILE APIs, ACCOUNT STATUS, PROFILE UPDATES & IDENTITY VALIDATION

## Objective

Implement secure, consistent user profile and identity-management APIs using the existing user and authentication infrastructure.

## Requirements

### A. Profile retrieval

1. Implement or verify an authenticated endpoint for retrieving the current user's profile.
2. Reuse the existing `/api/v1/auth/me` endpoint if it already provides the required behavior. Do not create a duplicate endpoint without a documented reason.
3. Implement an authorized administrative user-detail endpoint if required by the established API conventions.
4. Return only fields that the caller is authorized to view.
5. Never expose password hashes, raw tokens, reset credentials, internal security metadata, or secret values.

### B. Profile updates

1. Support updating explicitly permitted profile fields.
2. Use dedicated Pydantic request schemas with strict field allowlists.
3. Apply updates through the existing service layer.
4. Validate names, email addresses and other supported identity fields according to the established domain requirements.
5. Prevent mass assignment.
6. Do not allow ordinary profile updates to modify:
   - User role
   - Department ownership
   - Account activation status
   - Verification status
   - Password hash
   - Session state
   - Internal security flags
7. Preserve the previously implemented rule that self-profile updates are restricted to permitted fields, including `full_name`, unless the existing documented contract explicitly allows additional fields.
8. Require a separate authorized workflow for sensitive identity changes.

### C. Account status

1. Define or reuse the existing account-status model.
2. Support authorized retrieval of relevant status information.
3. Prevent disabled, suspended, or otherwise ineligible accounts from using protected operations according to the existing authentication policy.
4. Ensure status transitions cannot be performed by unauthorized users.
5. Ensure session and token behavior after account deactivation remains secure.
6. Do not invent a new account-status enumeration if an equivalent model already exists.

### D. Identity validation

1. Validate identity-related data on both API and service boundaries as appropriate.
2. Enforce normalized email uniqueness using the project's established email policy.
3. Handle duplicate identities safely and consistently.
4. Avoid leaking unnecessary personal information through errors.
5. Do not automatically change a verified email address without an appropriate verification workflow.
6. Do not introduce external identity-provider integrations unless they already exist in the roadmap and infrastructure.

### Required tests

- Retrieve own profile
- Retrieve another user's profile with and without permission
- Update permitted profile fields
- Reject role and department mass-assignment attempts
- Reject unauthorized account-status changes
- Duplicate and malformed email addresses
- Inactive-account behavior
- Sensitive-field redaction
- Existing authentication regression tests

# 5. PHASE 32 — STAFF ACCOUNT CREATION, INVITATION, ACTIVATION, DEACTIVATION & ADMINISTRATIVE CONTROLS

## Objective

Implement the secure lifecycle of staff accounts while respecting the established role-permission and department boundaries.

## Requirements

### A. Staff account creation

1. Implement authorized staff-account creation using existing models and service patterns.
2. Identify the permitted staff roles from the existing role matrix. Do not invent additional roles.
3. Validate required identity fields and department assignment.
4. Enforce uniqueness using application validation and database constraints where appropriate.
5. Ensure a department administrator cannot create a Super Admin or grant privileges outside their authorization.
6. Validate that the target department exists and is eligible to receive the account.
7. Prevent assigning an account to an unrelated department without the required privilege.
8. Do not return password hashes, secret tokens, or internal authentication fields.

### B. Invitations

1. Inspect existing email and notification infrastructure before implementation.
2. If invitation support already exists, extend the current workflow rather than creating another one.
3. Where a secure invitation workflow is missing, implement a suitable single-use, expiring invitation mechanism consistent with the established token infrastructure.
4. Store only a cryptographic digest of opaque invitation tokens where compatible with the existing token model.
5. Do not store raw invitation tokens in the database or logs.
6. Bind each invitation to its intended identity, allowed role, department, expiry, and lifecycle state.
7. Consume invitation tokens atomically so concurrent requests cannot activate the same invitation more than once.
8. Avoid account enumeration through invitation-related responses.
9. Do not claim email delivery succeeded if no real delivery provider is configured.
10. If email delivery is unavailable, provide an explicitly documented development/test workflow without exposing production secrets.

### C. Activation and deactivation

1. Implement authorized activation and deactivation operations where not already present.
2. Define safe and consistent lifecycle transitions.
3. Prevent unauthorized reactivation of deactivated accounts.
4. Ensure deactivation revokes or invalidates sessions according to the existing security model.
5. Check relevant token and session behavior after account-status changes.
6. Ensure a deactivated account cannot continue accessing protected resources merely because it possesses a previously issued token.
7. Do not permit an administrator to elevate their own role or circumvent privilege boundaries through account-management APIs.
8. Handle attempts to deactivate protected administrative accounts according to explicit policy.
9. Use transactional operations where multiple related state changes must succeed or fail together.

### D. Auditability

Reuse the existing logging or audit infrastructure where available. Record appropriate account lifecycle events without logging passwords, raw tokens, or unnecessary personal information.

Do not introduce a duplicate audit system.
